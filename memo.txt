状況の整理
- エレコム EX-G は多くのモデルが Bluetooth Classic (BR/EDR) を使っており、ポーリング型で遅延や負荷に強い設計。
- ZMK/Zephyr の自作は BLE (HID over GATT) で、接続パラメータや省電力、PHY などの設定次第でホストの負荷影響を受けやすい。
- そのため、BLE の接続パラメータ・優先度・スリープ・レポートレート・アンテナ/電源周りを詰めると改善しやすい。

優先して試すと改善しやすい設定（ZMK/Zephyr）
1) BLE 接続パラメータを低遅延に
- 目標: connection interval 7.5–11.25 ms、slave latency 0、supervision timeout 400–700 ms。
- Zephyr の Kconfig(プロジェクトやボードの prj.conf/overlay)で以下を設定（名称は Zephyr/ZMK のバージョンで多少異なることがあります）。
  - BT_PERIPHERAL_PREF_MIN_INT を 6（=7.5 ms）
  - BT_PERIPHERAL_PREF_MAX_INT を 9（=11.25 ms）
  - BT_PERIPHERAL_PREF_LATENCY を 0
  - BT_PERIPHERAL_PREF_TIMEOUT を 400～700
- これでホストが重い時でも通知間隔が長くならず、カクつきが減ります。
- 省電力重視の「スレーブレイテンシ」が効いていると動き出しでコマ落ちします。常時 0 にするか、「動かしている間だけ 0」に切り替える処理を入れると効果大。

2) PHY とリンクの堅牢化
- LE 2M PHY を有効化（ホストが対応していれば遅延と再送が減る）。
  - 例: BT_CTLR_PHY_2M と BT_USER_PHY_UPDATE を有効にして接続後に 2M を要求。
- データ長延長は HID では必須ではないが、リンクのゆとりが出る環境では安定性が上がる場合もあり。

3) レポートレートとレポート内容を調整
- ポインティングデバイスの送信レートを 125 Hz（8 ms）か 250 Hz（4 ms）程度に固定。
  - 接続間隔 7.5 ms と整合する 125 Hz がまず無難。過剰に高いとホスト負荷時にドロップが増えます。
- 変化がないフレームは送らない（デルタが 0 の時はレポートを抑制）。
- 拡張レポート（大きい HID レポート）を使わず、標準的な 8 バイト前後のマウスレポートにする。
- フィルタや加速で MCU から過剰な小刻み通知を出していないか確認（必要なら小さなデルタをまとめて送る＝コアレッシング）。

4) 電源管理・スレッド優先度
- 省電力で深いスリープに入ると割り込みからの復帰で遅延が出ます。
  - テストとして一旦 PM を無効化する、または深いスリープを禁止して軽いアイドルに留める。
- センサー読み取りと BLE 通知処理（HCI/LL）がキーボードスキャンに阻害されないよう、割り込み駆動＋高優先度に。
  - センサーは可能なら IRQ で駆動、I2C/SPI はクロックを上げる（I2C 400 kHz 以上、可能なら 1 MHz）。
  - Zephyr のスレッド優先度でポインティング→BLE→キーマトリクスの順に遅延しにくく。

5) 実機センサー周り
- トラックボールセンサーの CPI/DPI が過剰に高いと通知数が増え、混雑時にドロップ→ガタつきに見えることがあります。CPI を一段下げて挙動を確認。
- I2C トラックボールモジュールなら、バス速度・プルアップ・配線長を見直し、読み取りのばらつきを減らす。

6) アンテナ・筐体・給電
- BLE モジュールのアンテナ上に電池や金属を被せない、GND プレーンから少し逃がす、PC ケースからの遮蔽を避ける。
- 同一基板内の DC/DC や LED、モータ等のノイズ源から RF を離す。3.3V のリップルと瞬低が出ていないか確認（センサーと SoC 周りのデカップリング強化）。

PC 側で効く対策
- Bluetooth アダプタを BLE 5.0 以上・ドライバが安定したものに変更。PC 背面から USB 延長で前面/机上に出すと劇的に良くなることが多い。
- Windows のデバイスマネージャで Bluetooth アダプタ/マウスの電源管理「電力節約のため…電源をオフにできる」を無効化。
- 可能なら 2.4GHz 混雑（Wi‑Fi/他BT）を避ける：PC は 5GHz Wi‑Fi を使用、電子レンジ周辺を避ける。

確認とデバッグの手順
- 実際に交渉された接続パラメータを確認（Linux なら btmon、nRF Sniffer + Wireshark などで conn interval/latency/PHY を見る）。
- PC 高負荷時に ZMK 側で送出タイムスタンプをログ（RTT/USB CDC）し、送信間隔は保てているのにカーソルだけガタつくのか、そもそも送信が詰まっているのかを切り分け。
- USB 有線接続時に遅延が解消するなら、問題は BLE レイヤ/無線経路にほぼ限定できます。

発展的な選択肢
- デュアルモード運用：PC 接続時は自動で USB 優先（ZMK は USB/BLE 両対応可）。重い作業時は USB に逃がす。
- コントローラの切り替え：nRF SoC を使っているなら（Zephyr の LL 以外に）Nordic SoftDevice Controller を使う構成の方が安定するケースがあります（ZMK/Zephyr のバージョン適合要確認）。
- 2.4GHz 独自ドングル（ESB など）方式は遅延に強いですが、ZMK の標準外になります。

まずやってみる具体例（目安）
- 接続間隔: 7.5–11.25 ms、latency 0、timeout 500 ms
- PHY: 2M 有効
- レポートレート: 125 Hz
- センサー I2C: 400 kHz 以上
- PM: 深いスリープを暫定で無効化して評価

可能なら、現在の
- 使用 SoC/モジュール（例: nRF52840/ESP32 系など）
- 使用センサー（型番、I2C/SPI、現在の CPI/DPI）

- Windows/Mac/Linux と Bluetooth アダプタの型番
